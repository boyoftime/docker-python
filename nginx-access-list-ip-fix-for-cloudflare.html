Fix: Nginx Reading Cloudflare's IP Instead of the Visitor's Real IP

For Nginx Proxy Manager Access Lists, when your domain is proxied through Cloudflare

Table of Contents

  • The Problem
  • Prerequisites
  • The Fix: One Command Setup
  • Verify It Worked
  • Optional: Reverting & Long-Term Maintenance

The Problem

You created an Access List in Nginx Proxy Manager (e.g. allow only your own IP, deny everyone else) and attached it to a proxy host like phpmyadmin.yourdomain.com. Your IP looks correct in the rule, yet you keep getting:

403 Forbidden
openresty

The cause: NPM's allow / deny rules check the raw connecting IP ($remote_addr), not any forwarded header. If your domain is proxied through Cloudflare (the orange cloud in DNS), every visitor's request arrives at your server from Cloudflare's edge network — so nginx sees Cloudflare's IP, not the visitor's real IP, and your allow rule never matches.

You can confirm this yourself by tailing the proxy host's error log while loading the site:

docker exec -it nginx-proxy-manager tail -f /data/logs/proxy-host-3_error.log

If the client: field shows something like 104.22.x.x or 172.6x.x.x instead of your real IP, this is your problem.

Tip: Replace proxy-host-3 with your actual host ID. You can find it by running docker exec nginx-proxy-manager sh -c 'grep -l "yourdomain.com" /data/nginx/proxy_host/*.conf' — the number in the filename it returns is your host ID.

Prerequisites

  • Nginx Proxy Manager running in Docker (this guide assumes the container is named nginx-proxy-manager — check yours with docker ps).
  • Your domain's DNS is proxied through Cloudflare (orange cloud icon), and you have an Access List already attached to a proxy host.

The Fix: One Command Setup

This tells nginx to trust Cloudflare as a proxy and pull the real visitor IP from the CF-Connecting-IP header, so $remote_addr becomes the actual visitor IP again. Your existing Access List rules then work exactly as expected — no need to touch the rules themselves.

Copy and paste this whole block into your VPS's SSH terminal and press enter:

docker exec nginx-proxy-manager sh -c 'mkdir -p /data/nginx/custom && cat > /data/nginx/custom/server_proxy.conf << "EOF"
set_real_ip_from 103.21.244.0/22;
set_real_ip_from 103.22.200.0/22;
set_real_ip_from 103.31.4.0/22;
set_real_ip_from 104.16.0.0/13;
set_real_ip_from 104.24.0.0/14;
set_real_ip_from 108.162.192.0/18;
set_real_ip_from 131.0.72.0/22;
set_real_ip_from 141.101.64.0/18;
set_real_ip_from 162.158.0.0/15;
set_real_ip_from 172.64.0.0/13;
set_real_ip_from 173.245.48.0/20;
set_real_ip_from 188.114.96.0/20;
set_real_ip_from 190.93.240.0/20;
set_real_ip_from 197.234.240.0/22;
set_real_ip_from 198.41.128.0/17;
set_real_ip_from 2400:cb00::/32;
set_real_ip_from 2606:4700::/32;
set_real_ip_from 2803:f800::/32;
set_real_ip_from 2405:b500::/32;
set_real_ip_from 2405:8100::/32;
set_real_ip_from 2a06:98c0::/29;
set_real_ip_from 2c0f:f248::/32;
real_ip_header CF-Connecting-IP;
real_ip_recursive on;
EOF
nginx -t && nginx -s reload'

If it prints syntax is ok and test is successful with no errors, it worked. This applies automatically to every proxy host in NPM, not just one — you only need to run it once.

Why 127.0.0.1-style tricks don't apply here: Unlike proxying to 127.0.0.1 for the admin panel, this fix works by hooking into a file NPM already auto-includes in every generated server block (/data/nginx/custom/server_proxy.conf). That's why one command fixes it site-wide.

Verify It Worked

Tail the same error log again:

docker exec -it nginx-proxy-manager tail -f /data/logs/proxy-host-3_error.log

Reload the site in your browser. Either:

  • It loads successfully — the fix worked, no more block.
  • It's still forbidden, but the client: value in the new log line now shows your real IP instead of a Cloudflare IP — meaning the real-IP fix worked, and the block is just your Access List rule needing an update (e.g. your IP changed).
Optional — read only if needed

Reverting & Long-Term Maintenance

You don't need to do anything below unless one of these situations applies to you.

If you stop using Cloudflare later

Good news: you don't have to remove anything. The rule only activates when the connecting IP matches a Cloudflare range. Without Cloudflare in front, no visitor IP will ever match those ranges, so the whole block quietly does nothing, and nginx just uses the real connecting IP as-is (which is already correct with no proxy in between).

If you'd still like to remove it for tidiness, run:

docker exec nginx-proxy-manager sh -c 'rm -f /data/nginx/custom/server_proxy.conf && nginx -t && nginx -s reload'

If Cloudflare updates their IP ranges

Cloudflare rarely changes these ranges, but if you ever suspect it (e.g. a previously-working rule starts failing again with a new, unlisted 104.x.x.x-style IP in the logs), check the current official list here:

https://www.cloudflare.com/ips/

If it changed, just re-run the same setup command from Section 3 with the updated ranges — it will safely overwrite the old file.
