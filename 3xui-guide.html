What is 3X-UI?

3X-UI is an advanced, open-source web panel for managing Xray-core — the popular network protocol engine used to run VMess, VLESS, Trojan, Shadowsocks, and other proxy/VPN protocols. It is a fork of the original X-UI project and is actively maintained at MHSanaei/3x-ui.

Instead of hand-editing JSON config files, 3X-UI gives you a clean web UI to add inbound connections, generate client configs, monitor traffic usage, and manage user accounts.

Use Case: This guide is geared toward operators running their own proxy/VPN infrastructure for personal use, small teams, or bypassing geographic restrictions to services you are legitimately entitled to use. Always comply with your local laws and your VPS provider's Terms of Service.

Prerequisites

This guide assumes you have already completed the main "Deploying Multiple Flask Apps" guide. Specifically, you need:

  • A VPS with Docker and Docker Compose installed.
  • The shared Docker network nginx-proxy already created.
  • Nginx Proxy Manager up and running (for the domain / SSL step).
  • A domain name (e.g. panel.yourdomain.com) pointed to your server's IP, if you plan to secure the panel via a domain.

Part 1: Firewall & Port Planning

The 3X-UI web panel listens on port 2053 by default. This port has been added to the server port registry so it does not collide with any other services on your VPS.

Why host network mode? The official 3X-UI Docker deployment uses network_mode: host, and this guide follows suit. Xray-core needs to open arbitrary inbound ports that you choose per protocol (VMess / VLESS / Trojan / Shadowsocks), and in host mode any port you bind inside the panel is automatically reachable from outside — no compose edits, no container restarts. The only consequence is that 3X-UI does not join the nginx-proxy Docker network; instead, NPM forwards traffic to the host's IP on port 2053. That still gives you a fully working https://panel.yourdomain.com.

Ports to Open in Your VPS Firewall

  • Port 2053 (TCP): The 3X-UI admin panel. After you finish the Nginx Proxy Manager step, you can close this to the public internet and access it only through your domain on port 443.
  • Inbound ports per protocol: Whatever ports you configure inside the panel for each inbound (e.g. VMess on 10000, Trojan on 443) must also be allowed in your VPS provider's firewall dashboard. Because we use host mode, you do not need to edit the compose file each time — just open the port at the cloud firewall level.

Part 2: Deploying 3X-UI with Docker Compose

Step 1: Create the Project Directory

mkdir -p /root/docker-deployment/3xui
cd /root/docker-deployment/3xui

Step 2: Create the docker-compose.yml

Inside /root/docker-deployment/3xui/, create a file named docker-compose.yml with the following content (from the official installation docs):

# /root/docker-deployment/3xui/docker-compose.yml
services:
  3xui:
    image: ghcr.io/mhsanaei/3x-ui:latest
    container_name: 3xui_app
    restart: unless-stopped
    tty: true
    volumes:
      - ./db/:/etc/x-ui/
      - ./cert/:/root/cert/
    environment:
      XRAY_VMESS_AEAD_FORCED: "false"
      XUI_ENABLE_FAIL2BAN: "true"
    # Host network mode: the container shares the VPS's network stack directly.
    # Every port you bind inside the panel is automatically reachable —
    # no 'ports:' list to maintain. This is the official recommended setup.
    network_mode: host

What each part does:

  • image: ghcr.io/mhsanaei/3x-ui:latest — Official image from GitHub Container Registry.
  • ./db/ — Persists the panel database (users, inbounds, settings) to the host.
  • ./cert/ — Holds the TLS certificate files you upload for Xray inbounds (see Part 5).
  • XRAY_VMESS_AEAD_FORCED: "false" — Keeps compatibility with older VMess clients.
  • XUI_ENABLE_FAIL2BAN: "true" — Enables built-in brute-force login protection.
  • network_mode: host — Container binds ports directly on the host. Any inbound you add in the panel is auto-exposed — no compose edits needed.
  • restart: unless-stopped — Container auto-starts on reboot.

💡 No more compose edits for new inbounds: Because we're using host network mode, when you create a new VMess / VLESS / Trojan / Shadowsocks inbound inside the 3X-UI panel on any port, it is instantly reachable. You only need to open that port in your VPS provider's firewall — no docker compose restart required.

Step 3: Start the Container

cd /root/docker-deployment/3xui
docker compose up -d

Verify it's running:

docker compose ps
docker compose logs -f

Part 3: First Login & Changing Credentials

With the container running, open the panel in your browser at:

http://YOUR_SERVER_IP:2053

Default Credentials

  • Username: admin
  • Password: admin

⚠ Critical Security Step: Immediately after your first login, go to Panel Settings → Security and change both the username and the password. The default admin/admin credentials are scanned for constantly by bots on the public internet.

Additional Hardening (Recommended)

  • Enable Two-Factor Authentication (2FA) under Panel Settings → Security.
  • Change the panel's web path (e.g. from / to /mysecretpath) to hide it from automated scanners.
  • Change the panel port from 2053 to something non-default if desired (remember to update the port registry and firewall if you do).

Part 4: Securing with Nginx Proxy Manager (Domain + SSL)

Exposing http://YOUR_SERVER_IP:2053 directly is insecure — there's no SSL, and the IP-based URL makes it an obvious target. We'll use Nginx Proxy Manager to put it behind https://panel.yourdomain.com.

Step 1: Point Your Domain to the Server

At your DNS provider, create an A record:

  • Name: panel (or whatever subdomain you want)
  • Value: Your VPS public IP
  • TTL: Automatic / 300

Step 2: Add a Proxy Host in Nginx Proxy Manager

  1. Open NPM at http://YOUR_SERVER_IP:81 (or your secured NPM domain).
  2. Go to Hosts → Proxy Hosts and click Add Proxy Host.
  3. Details Tab:
    • Domain Names: panel.yourdomain.com
    • Scheme: http
    • Forward Hostname / IP: YOUR_SERVER_IP (your VPS's public IP address).

      Why the host IP and not a container name? Because 3X-UI runs with network_mode: host, it is not on the nginx-proxy Docker network, so NPM cannot reach it by container name. Instead, forward traffic to the host's IP on port 2053. NPM reaches it over the host network just like any other HTTP client — SSL, Force SSL, and Websockets all still work normally.

    • Forward Port: 2053
    • Turn on Block Common Exploits.
    • Turn on Websockets Support (3X-UI uses WebSockets for live traffic stats).
  4. SSL Tab:
    • SSL Certificate: Select "Request a new SSL Certificate" (Let's Encrypt).
    • Turn on Force SSL.
    • Turn on HTTP/2 Support.
    • Agree to the Terms of Service and click Save.

Step 3: Close Port 2053 to the Public

Once https://panel.yourdomain.com is working, you no longer need port 2053 open to the internet. NPM reaches 3X-UI through the host's local network interface, which is independent of your cloud firewall. In your VPS provider's firewall dashboard, remove the inbound rule for port 2053. The panel will now only be reachable through your secured domain.

✨ Your 3X-UI panel is now live at https://panel.yourdomain.com with a valid SSL certificate.

Part 5: TLS Certificates for Xray Inbounds

Any inbound you create in the 3X-UI panel (VLESS, VMess, Trojan, etc.) with TLS enabled needs a real certificate and private key on disk. If the paths you enter don't point to actual files, Xray-core fails to start and you'll see a red banner on the Xray Configs page:

failed to build Inbound config with tag inbound-XX
 -> failed to parse certificate
 -> open /path/to/cert: no such file or directory

How the folders map: Your compose file mounts ./cert/ (on the host, at /root/docker-deployment/3xui/cert/) to /root/cert/ inside the container. Anything you drop in the host folder is instantly visible to Xray at the container path.

Step 1: Download the Cert from Nginx Proxy Manager

In NPM's UI, go to SSL Certificates, find the row for your VPN domain (e.g. vpn.yourdomain.com), click the … menu, and choose Download. You get a zip containing four files:

  • fullchain1.pem — upload this (your cert + Let's Encrypt intermediate)
  • privkey1.pem — upload this (the private key)
  • cert1.pem — skip (already included in fullchain)
  • chain1.pem — skip (already included in fullchain)

Step 2: Rename and Upload via SFTP (FileZilla / WinSCP)

Rename the two files on your local machine to drop the 1:

  • fullchain1.pem → fullchain.pem
  • privkey1.pem → privkey.pem

Then upload both files to:

/root/docker-deployment/3xui/cert/

Step 3: Secure the Private Key

SSH into the VPS and lock down the private key so only root can read it:

chmod 600 /root/docker-deployment/3xui/cert/privkey.pem
chmod 644 /root/docker-deployment/3xui/cert/fullchain.pem

Step 4: Verify the Files Are Visible Inside the Container

docker exec 3xui_app ls -l /root/cert/

You should see both fullchain.pem and privkey.pem. If they're missing, the upload didn't land in the right folder.

Step 5: Point the Inbound at the Cert Files

In the 3X-UI panel, go to Inbounds, edit the inbound that was failing, scroll to the TLS / Security section, and enter these container paths (not host paths):

  • Public Key Path (Cert): /root/cert/fullchain.pem
  • Private Key Path: /root/cert/privkey.pem

Click Save. Within a few seconds the red banner on the Xray Configs page disappears and the inbound goes green.

⚠ Renewal reminder: Let's Encrypt certs expire every 90 days. NPM auto-renews its own copy, but the files you uploaded here are a one-time snapshot. Set a calendar reminder every ~60 days to re-download from NPM and re-upload the two renamed files to the same folder. If you forget, clients will start failing with TLS errors the moment the cert expires.

Sanity Check

If Xray still won't start after saving, confirm the cert file is actually readable from inside the container:

docker exec 3xui_app cat /root/cert/fullchain.pem | head -2

If you see -----BEGIN CERTIFICATE-----, the file is fine and the problem is a mismatched path in the inbound. If you get an error, re-do Steps 2 and 4.

Part 6: Updating 3X-UI

To pull the latest version of 3X-UI and restart the container:

cd /root/docker-deployment/3xui
docker compose down
docker compose pull
docker compose up -d

Your db/ and cert/ folders are preserved, so all your inbounds, users, and certificates survive the update.

Part 7: Decommissioning & Cleanup

If you want to completely remove 3X-UI from your server, follow these steps in order.

Step 1: Remove the Proxy Host in NPM

Log in to Nginx Proxy Manager and delete the proxy host for panel.yourdomain.com. Also delete its SSL certificate under SSL Certificates if you won't be reusing it.

Step 2: Take Down the Container

cd /root/docker-deployment/3xui
docker compose down

Step 3: Remove the Docker Image

# Remove the specific 3X-UI image
docker rmi ghcr.io/mhsanaei/3x-ui:latest

Step 4: Delete Project Files (Database & Certs)

⚠ Warning: This is irreversible. All inbounds, users, usage statistics, and uploaded certificates will be permanently lost.

# Delete the entire 3X-UI project folder (db + cert + compose file)
rm -rf /root/docker-deployment/3xui

Step 5 (Optional): Prune Dangling Docker Resources

If you want to clean up unused Docker layers and volumes left behind:

# Remove stopped containers, unused networks, dangling images, and build cache
docker system prune -a

# Also remove unused volumes (be careful — this affects ALL Docker projects)
docker volume prune

Step 6: Close the Firewall Port

If you hadn't already closed port 2053 (and any Xray inbound ports you configured) in your VPS provider's firewall, remove those rules now.
