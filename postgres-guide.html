Prerequisites & Architecture

This guide assumes you have already completed the main "Deploying Multiple Flask Apps" guide. Specifically, you must have:

  • A VPS with Docker and Docker Compose installed.
  • The shared Docker network named nginx-proxy created.
  • The Nginx Proxy Manager container up and running.

Architecture Reminder: We are creating a new, independent service for our database. This decouples your data from your application logic. The primary connection method is over the secure, internal Docker network, which is fast and does not require exposing the database to the internet.

Why PostgreSQL? PostgreSQL is a powerful, open-source relational database known for its standards compliance, advanced data types (JSONB, arrays, geospatial), and rock-solid reliability. pgAdmin is its official web-based management GUI — the equivalent of phpMyAdmin for MySQL. This guide mirrors our MySQL setup but uses the Postgres ecosystem.

Official pgAdmin container docs: pgadmin.org/docs/pgadmin4/container_deployment.

Part 1: Setting Up the Database Service

Step 1: Create the Project Directory

On your server, create a dedicated directory for your PostgreSQL stack. This keeps it neatly separated from your other services (including a MySQL stack, if you run both).

# This directory will live alongside your 'proxy-manager' and 'apps' folders
mkdir /root/docker-deployment/postgres

Step 2: Create the Database `docker-compose.yml`

This single file defines both the PostgreSQL database and the pgAdmin management interface. The default configuration below is the most secure, as it does not expose the database port to the internet.

# Create and open the file for editing
nano /root/docker-deployment/postgres/docker-compose.yml

Paste the following content into the file. This is the standard, secure configuration.

services:
  # --- The PostgreSQL Database Service ---
  db:
    image: postgres:18
    container_name: postgres_db
    restart: unless-stopped
    environment:
      # REQUIRED. This sets the password for the default 'postgres' superuser.
      # Must be a non-empty value or the container will refuse to start.
      # We intentionally OMIT POSTGRES_USER and POSTGRES_DB so that no app
      # role/database is auto-created — you'll create those yourself in the
      # pgAdmin UI (see Part 3). Postgres then defaults to:
      #   superuser = postgres   |   default database = postgres
      POSTGRES_PASSWORD: YOUR_VERY_STRONG_PASSWORD
    volumes:
      # CRITICAL: This line persists your database data on the host machine.
      # NOTE: Postgres 18+ uses this path. For v17 and below it is
      # /var/lib/postgresql/data instead.
      - ./postgres-data:/var/lib/postgresql/18/docker
    networks:
      - nginx-proxy

  # --- The pgAdmin GUI Service ---
  pgadmin:
    image: dpage/pgadmin4:latest
    container_name: pgadmin_gui
    restart: unless-stopped
    environment:
      # IMPORTANT: These are the credentials you use to LOG IN to pgAdmin itself.
      PGADMIN_DEFAULT_EMAIL: admin@yourdomain.com
      PGADMIN_DEFAULT_PASSWORD: YOUR_STRONG_PGADMIN_PASSWORD
      # Optional: hide the "set master password" prompt for a single-user setup.
      PGADMIN_CONFIG_MASTER_PASSWORD_REQUIRED: "False"
    volumes:
      # Persist pgAdmin's own settings and saved server connections.
      - pgadmin-data:/var/lib/pgadmin
    ports:
      - "8083:80" # Map host port 8083 to the container's internal port 80
    depends_on:
      - db # Ensures the database starts before pgAdmin.
    networks:
      - nginx-proxy

# A named volume for pgAdmin avoids file-permission issues that bind mounts
# cause (the container runs as the non-root 'pgadmin' user, uid 5050).
volumes:
  pgadmin-data:

# Declare that our shared network is external and pre-existing.
networks:
  nginx-proxy:
    external: true

Remember to replace the placeholder passwords and email before saving the file!

Why only one database variable? Of the three PostgreSQL variables, only POSTGRES_PASSWORD is required:

  • POSTGRES_PASSWORD — 🔴 required, no default. Sets the password for the built-in postgres superuser. An empty value ("") counts as missing and the container will crash-loop.
  • POSTGRES_USER — 🟢 optional, defaults to postgres.
  • POSTGRES_DB — 🟢 optional, defaults to the username (so also postgres).

This guide deliberately omits the last two and creates the real application user and database through the pgAdmin UI in Part 3. That gives you full control and lets you make a separate, least-privilege user per app. (If you'd rather have one auto-created on first boot, just add POSTGRES_USER: and POSTGRES_DB: back.)

⚠️ Avoid the $ character in passwords (or escape it)! Docker Compose treats $ as a variable reference, even inside quotes. A password like $ecret makes Compose look for a variable named ecret, fail to find it, and silently pass a blank password — you'll see WARN The "ecret" variable is not set. Defaulting to a blank string and Postgres will refuse to start with "superuser password is not specified".

To use a literal $, escape it by doubling it: write "$$ecret" for the password $ecret. The simplest fix is to just not start passwords with $.

⚠️ The data path is version-specific — keep the image tag and volume path in sync! This guide pins postgres:18, which stores its data at /var/lib/postgresql/18/docker (note the version number in the path). PostgreSQL 17 and below used /var/lib/postgresql/data instead. If you change the image tag, you must update the right-hand side of the volume line to match, or Postgres will silently start with an empty data directory and your data won't persist. Always pin an explicit major version, and only upgrade deliberately (with a backup first).

⚠️ Why a named volume for pgAdmin? Unlike the Postgres data folder, pgAdmin's /var/lib/pgadmin directory is owned by an internal non-root user. If you bind-mount a host folder there (e.g. ./pgadmin-data), the container will fail to start with permission errors. The Docker-managed named volume (pgadmin-data) handles ownership correctly — this is the method recommended by the official docs.

Step 3: Launch the Database Service

Navigate to the new directory and start the services.

# Navigate into the postgres project directory
cd /root/docker-deployment/postgres

# Start the services in detached mode (-d)
docker compose up -d

Docker will now download the images and start your database stack. A folder named postgres-data will appear, safely storing your database.

You can access the pgAdmin login page directly at http://YOUR_SERVER_IP:8083.

Part 2: Securely Accessing pgAdmin

We will use Nginx Proxy Manager to give pgAdmin a secure, easy-to-remember domain name with an SSL certificate.

  1. Point a Subdomain: In your domain registrar (e.g., Namecheap), create a new 'A' record for a subdomain like pgadmin.yourdomain.com and point it to your server's IP address.
  2. Log in to Nginx Proxy Manager.
  3. Add a New Proxy Host:
    • Details Tab:
      • Domain Names: pgadmin.yourdomain.com
      • Scheme: http
      • Forward Hostname / IP: pgadmin (This MUST be the service name from your `docker-compose.yml`).
      • Forward Port: 80 (The internal port of the pgAdmin container).
      • Turn on "Websockets Support" — pgAdmin uses websockets for some features.
    • SSL Tab: Select "Request a new SSL Certificate" and turn on "Force SSL".
    • Save.

After a minute, you can access your secure pgAdmin interface at https://pgadmin.yourdomain.com. Log in with the PGADMIN_DEFAULT_EMAIL and PGADMIN_DEFAULT_PASSWORD you set.

Part 3: Connecting pgAdmin to PostgreSQL

Unlike phpMyAdmin (which auto-connects via PMA_HOST), pgAdmin is a generic tool that can manage many database servers, so it doesn't know about yours until you register it once. Think of it like saving a new contact in your phone, or entering a destination in a GPS — pgAdmin only needs to be told where the database is and how to log in.

Two different logins — don't mix them up:

  • Logging in to pgAdmin (the website) uses PGADMIN_DEFAULT_EMAIL / PGADMIN_DEFAULT_PASSWORD.
  • Connecting to the database (the step below) uses the PostgreSQL account: username postgres and your POSTGRES_PASSWORD.

Step 1: Open the Register dialog

  1. Log in to pgAdmin at http://YOUR_SERVER_IP:8083 (or your secure domain).
  2. In the left sidebar, right-click "Servers" → "Register" → "Server…" (or click "Add New Server" on the dashboard).

Step 2: Fill in ONLY these fields

The dialog has many tabs (General, Connection, Parameters, SSH Tunnel, Advanced, Post Connection SQL, Tags). You only need two tabs. Leave every other tab at its defaults.

① General tab

  • Name: any friendly label, e.g. My VPS Postgres. This is the only required field here — leaving it blank gives the error "'Name' cannot be empty." It's just a display name; it has no effect on the connection.

② Connection tab — these are the fields that actually matter:

Field Value Why
Host name / addressdbThe service name of the Postgres container. Works because pgAdmin and the DB share the nginx-proxy network. (Not the public IP.)
Port5432PostgreSQL's default port.
Maintenance databasepostgresThe database pgAdmin connects to first. postgres always exists.
UsernamepostgresThe superuser created by POSTGRES_PASSWORD. (NOT your pgAdmin email!)
Passwordyour POSTGRES_PASSWORDAuthenticates the postgres user.
Save password?ONSo you don't retype it every time.

Ignore these tabs for a normal setup — the defaults are correct:

  • Parameters — SSL mode / connection timeout. Defaults (sslmode: prefer, timeout: 10) are fine.
  • SSH Tunnel — only needed if connecting through a bastion/jump host. Leave OFF.
  • Advanced — DB restrictions, prepare threshold, etc. Leave blank.
  • Post Connection SQL — runs SQL on every connect. Leave empty.
  • Tags — purely cosmetic colored labels. Optional.

Step 3: Save

Click Save. Your server appears in the sidebar and connects. Expanding it shows Databases → postgres — the only database so far. Next you'll create your own.

Step 4: Create your application database and user (in the UI)

Because we omitted POSTGRES_USER/POSTGRES_DB, there's no app-specific account yet. Create one following the Principle of Least Privilege. The fastest way is the Query Tool:

  1. Right-click the postgres database → Query Tool.
  2. Paste and run (press F5):
-- A dedicated login role for your app
CREATE ROLE flask_user WITH LOGIN PASSWORD 'a_strong_password';

-- A database owned by that role
CREATE DATABASE flask_db OWNER flask_user;

Or do it with clicks: right-click Login/Group Roles → Create → Login/Group Role (set a name, a password on the Definition tab, and Can login? = Yes on the Privileges tab), then right-click Databases → Create → Database (set the name and pick the owner).

You now have flask_user + flask_db — the same result as auto-creating them in compose, but made by hand and fully under your control. Your application (Part 4) connects with these credentials.

Part 4: Connecting Your Application

Now, let's connect your deployed Flask application to this new database.

Step 1: Update Application Dependencies

Your application needs a PostgreSQL driver. For a Flask app, your requirements.txt should include:

# In your app's requirements.txt
flask
gunicorn
psycopg2-binary   # PostgreSQL driver
SQLAlchemy        # optional, but recommended for ORM access

Step 2: Configure the Connection String

In your Flask app.py, configure the connection details. The key is using the database service name (db) as the host, which only works when both containers are on the same Docker network.

# In your app.py
# --- Database Configuration ---
# Format: postgresql://USER:PASSWORD@HOST:PORT/DATABASE
DB_USER = "your_app_user"
DB_PASSWORD = "your_app_password"
DB_HOST = "db"          # The service name of the PostgreSQL container
DB_PORT = "5432"
DB_NAME = "your_app_database"

app.config["SQLALCHEMY_DATABASE_URI"] = (
    f"postgresql+psycopg2://{DB_USER}:{DB_PASSWORD}@{DB_HOST}:{DB_PORT}/{DB_NAME}"
)

# ... rest of your application code ...

Step 3: Rebuild and Restart Your App

Since you've changed the requirements and code, you must rebuild your app's Docker image.

# Navigate to your specific application's directory
cd /root/docker-deployment/apps/your_app_name

# Rebuild the image and restart the containers
docker compose up --build -d

Your application will now connect to the central PostgreSQL container over the shared nginx-proxy network.

Part 5: Database Management

Useful Docker Commands

Run these commands from within the /root/docker-deployment/postgres/ directory.

# See the logs for the PostgreSQL container (useful for debugging)
docker compose logs -f db

# Open an interactive psql shell inside the running container
docker compose exec db psql -U flask_user -d flask_db

# Stop the database services without deleting data
docker compose stop

# Start the database services again
docker compose start

# Stop and REMOVE the containers (your data is safe in the 'postgres-data' folder)
docker compose down

Creating New Databases and Users (Principle of Least Privilege)

For each new application, create a dedicated database and role so apps cannot touch each other's data. You can do this in pgAdmin's GUI, or quickly via the psql shell:

-- Open psql first:  docker compose exec db psql -U flask_user -d flask_db

-- 1. Create a dedicated login role with a strong password
CREATE ROLE app2_user WITH LOGIN PASSWORD 'a_strong_password';

-- 2. Create a database owned by that role
CREATE DATABASE app2_db OWNER app2_user;

-- 3. (Optional) ensure only the owner can connect
REVOKE CONNECT ON DATABASE app2_db FROM PUBLIC;
GRANT CONNECT ON DATABASE app2_db TO app2_user;

You now have a new, secure, isolated database and user for your project.

Backing Up Your Data

The recommended way to back up PostgreSQL is a logical dump with pg_dump, which is portable and consistent without stopping the database.

cd /root/docker-deployment/postgres

# Dump a single database to a compressed file on the host
docker compose exec -T db pg_dump -U flask_user -d flask_db \
  | gzip > /root/postgres_backup_$(date +%F).sql.gz

# Or dump ALL databases at once
docker compose exec -T db pg_dumpall -U flask_user \
  | gzip > /root/postgres_full_backup_$(date +%F).sql.gz

To restore from a dump:

# Restore a single-database dump into an existing (empty) database
gunzip -c /root/postgres_backup_2026-05-21.sql.gz \
  | docker compose exec -T db psql -U flask_user -d flask_db

You can download the .sql.gz file using an SFTP client.

Part 6: Allowing External Connections (Advanced)

⚠️ Security Warning: Exposing your database to the public internet is a significant security risk. Only do this for temporary needs like local development and ensure you have strong passwords. It is always more secure to have your applications connect over the private Docker network.

If you must allow external connections (e.g., from your local PC for development), follow these three steps.

Step 1: Update `docker-compose.yml`

You need to modify your postgres/docker-compose.yml to map the PostgreSQL port to your host server. Add the ports section to the db service.

  # --- The PostgreSQL Database Service ---
  db:
    image: postgres:18
    container_name: postgres_db
    restart: unless-stopped
    environment:
      POSTGRES_PASSWORD: YOUR_VERY_STRONG_PASSWORD
      POSTGRES_USER: flask_user
      POSTGRES_DB: flask_db
    ports:
      # Maps your server's public port 5432 to the container's private port 5432.
      - "5432:5432"
    volumes:
      - ./postgres-data:/var/lib/postgresql/18/docker
    networks:
      - nginx-proxy

Step 2: Apply the Change and Open Firewall

  1. Restart the Service: Navigate to the postgres directory and run `up` to apply the port mapping. 
    cd /root/docker-deployment/postgres
docker compose up -d
  2. Open Firewall Port: In your VPS provider's firewall settings, create a rule to ALLOW inbound TCP traffic on port 5432. For added security, restrict the source to your home or office IP address.

💻 When does this apply? These steps are only needed when something outside the Docker network connects to the database — for example, a Flask app running on your local PC, a desktop SQL client, or a separate server. Anything that lives in the same Docker network as the database (such as a Flask app deployed on the VPS) should connect using the service name db as the host and does not need the port exposed at all — that path is faster and more secure.

If an external/local client fails with an error like:

connection to server at "YOUR_SERVER_IP", port 5432 failed:
Connection refused ... Is the server running on that host and accepting TCP/IP connections?

…the port simply isn't reachable from outside yet. The database listens only on the private Docker network until you complete both parts of Step 2: (1) add the ports: - "5432:5432" mapping and (2) open inbound TCP 5432 in your VPS firewall. Confirm the container is publishing the port with docker compose ps — you should see 0.0.0.0:5432->5432/tcp.

Step 3: Connect from Your Local Application

You can now configure your local development application to connect using your server's public IP as the host.

# In your LOCAL app.py for development
DB_HOST = "YOUR_SERVER_IP"  # Use the server's public IP
DB_PORT = "5432"
# postgresql+psycopg2://your_app_user:your_app_password@YOUR_SERVER_IP:5432/your_app_database

Part 7: Example — A Flask App That Displays Your Data

Here is a complete, minimal Flask app that connects to your PostgreSQL database and renders a table in the browser. It assumes you have a users table with id, username, age, and country columns. Create it first in pgAdmin's Query Tool:

CREATE TABLE users (
    id       SERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    age      INTEGER,
    country  VARCHAR(50)
);

-- Generate 50 rows of random sample data
INSERT INTO users (username, age, country)
SELECT
    'user_' || substr(md5(random()::text), 1, 6),
    floor(random() * 50 + 18)::int,
    (ARRAY['USA','UK','Canada','Germany','Japan','Brazil',
           'India','Nigeria','Australia','France'])[floor(random()*10 + 1)]
FROM generate_series(1, 50);

Project Structure

sample/
├── app.py
├── requirements.txt
└── templates/
    └── index.html

File 1: requirements.txt

flask
psycopg2-binary

File 2: app.py

Connection details are read from environment variables, falling back to defaults. When deployed on the VPS, set DB_HOST=db (the service name) and you do not need to expose port 5432 at all. When running on your local PC, DB_HOST must be the server's public IP and you must complete Part 6 (expose the port + open the firewall).

import os

import psycopg2
import psycopg2.extras
from flask import Flask, render_template

app = Flask(__name__)

# --- Database connection settings ---
DB_HOST = os.environ.get("DB_HOST", "YOUR_SERVER_IP")  # use "db" when on the VPS
DB_PORT = os.environ.get("DB_PORT", "5432")
DB_NAME = os.environ.get("DB_NAME", "flask_db")
DB_USER = os.environ.get("DB_USER", "flask_user")
DB_PASSWORD = os.environ.get("DB_PASSWORD", "YOUR_PASSWORD")


def get_connection():
    return psycopg2.connect(
        host=DB_HOST, port=DB_PORT, dbname=DB_NAME,
        user=DB_USER, password=DB_PASSWORD,
    )


@app.route("/")
def index():
    error = None
    users = []
    try:
        conn = get_connection()
        cur = conn.cursor(cursor_factory=psycopg2.extras.DictCursor)
        cur.execute("SELECT id, username, age, country FROM users ORDER BY id;")
        users = cur.fetchall()
        cur.close()
        conn.close()
    except Exception as exc:  # show the problem in the browser instead of a 500
        error = str(exc)

    return render_template("index.html", users=users, error=error)


if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000, debug=True)

Part 8: Decommissioning the Database

If you no longer need your database, it's important to remove it cleanly to free up system resources. Follow these steps in order to permanently remove PostgreSQL, pgAdmin, and all associated data.

  1. Remove the Proxy Host: First, remove the public-facing entry point. Log into Nginx Proxy Manager, find the host for your pgAdmin (e.g., pgadmin.yourdomain.com), click the three-dot menu, and delete it.
  2. Take Down the Docker Services: Navigate to the postgres project directory and run the `down` command. The `-v` flag removes named volumes (including pgAdmin's settings). 
    # Navigate to the postgres project directory
cd /root/docker-deployment/postgres

# Stop and remove the containers and named volumes
docker compose down -v
  3. Permanently Delete All Database Data: This is the most critical and irreversible step. The following command deletes the folder containing all of your PostgreSQL databases.

    ⚠️ WARNING: This action will permanently delete all your database data. There is no undo. Make sure you have a backup if you ever want to restore this data.

    # This deletes the postgres-data folder and everything inside it
rm -rf /root/docker-deployment/postgres/postgres-data
  4. Delete the Project Directory: Finally, clean up the remaining project files, including the `docker-compose.yml`. 
    # Go up one directory level
cd /root/docker-deployment

# Delete the entire postgres project folder
rm -rf postgres

The central PostgreSQL database and pgAdmin have now been completely removed from your server.
