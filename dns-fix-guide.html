The Problem

You may encounter one or both of these issues on your VPS:

  • Docker builds fail with the error: dial tcp: lookup registry-1.docker.io: i/o timeout
  • Outgoing API calls (e.g., to payment gateways like ClickPesa) intermittently fail with "unable to complete request"

Both symptoms point to the same underlying issue: the server cannot reliably resolve domain names to IP addresses.

The Root Cause

The default DNS resolver on most Ubuntu VPS instances is systemd-resolved, which listens locally at 127.0.0.53. When its upstream DNS is slow or unreliable, anything needing to look up a domain (Docker pulling images, your Flask app calling an external API) will time out or fail.

How to confirm this is your issue:

cat /etc/resolv.conf

You'll always see nameserver 127.0.0.53 here — that's normal and expected, this file never changes even after the fix below. It only tells programs "ask the local stub," not what the stub forwards to. Don't judge success or failure by this file; Step 3 shows you the real check.

Step 1: Set Cloudflare DNS Globally

This creates a small config override telling systemd-resolved to use Cloudflare as its upstream DNS, then restarts it. Nothing to disable, nothing that reverts on reboot.

Copy and paste this whole block into your VPS's SSH terminal:

sudo mkdir -p /etc/systemd/resolved.conf.d && sudo tee /etc/systemd/resolved.conf.d/dns-override.conf > /dev/null << 'EOF'
[Resolve]
DNS=1.1.1.1 1.0.0.1
FallbackDNS=8.8.8.8 8.8.4.4
EOF
sudo systemctl restart systemd-resolved

If you rely on Docker for builds or outgoing API calls, rebuild your containers once DNS is fixed so they pick up working resolution:

docker compose up --build -d

Step 2: Check for a Provider-Locked DNS Override

Some VPS providers hardcode their own DNS servers directly into your network config. If they do, that setting wins over the global Cloudflare setting from Step 1 — so it's worth a 10-second check.

1Look at your netplan file:
cat /etc/netplan/*.yaml

If you see a block like this, with real IP addresses under nameservers, your provider has locked in their own DNS:

nameservers:
  addresses:
  - 195.179.224.53
  - 209.126.15.53
2Replace those two IPs with Cloudflare's:

Swap 195.179.224.53 and 209.126.15.53 below for whatever two IPs you actually saw in your file, then run:

sudo sed -i 's/195.179.224.53/1.1.1.1/; s/209.126.15.53/1.0.0.1/' /etc/netplan/*.yaml
sudo netplan apply

If you didn't see any hardcoded IPs in Step 1, your provider isn't overriding anything — skip this step entirely and go straight to Step 3.

Step 3: Confirm It's Actually Working

Check which DNS server is genuinely in use:

resolvectl status

Look for Current DNS Server: 1.1.1.1 near the top, under Global.

Then do a live lookup through the normal system path:

dig google.com

Compare the IPs in the ANSWER SECTION against a direct Cloudflare query:

dig @1.1.1.1 google.com +short

If both return matching/fresh results (not old, stale-looking answers), Cloudflare is genuinely handling your DNS now — not just configured and ignored.

Optional — only if you need to undo this

Reverting to Default DNS

To undo Step 1 (the global override):

sudo rm -f /etc/systemd/resolved.conf.d/dns-override.conf
sudo systemctl restart systemd-resolved

To undo Step 2 (if you changed your netplan file), just edit /etc/netplan/*.yaml again and put the original provider IPs back under nameservers, then run sudo netplan apply.

Run resolvectl status afterward to confirm you're back to the original DNS servers.
